# Notes

Gotchas and non-obvious behaviors discovered while working on ForceAutoHDR.Net.
One file per trap. Keep entries short: the trap, the fix, and a pointer into
the code so future-you can find the guard.

## Index

- [winui3-aot-publish-drops-pri-without-msixtooling.md](winui3-aot-publish-drops-pri-without-msixtooling.md) — `EnableMsixTooling=false` in an unpackaged WinUI 3 project silently drops `<App>.pri` from the publish output; the AOT exe then dies at startup with `0xC000027B` / E_FAIL in `Microsoft.UI.Xaml.dll`. Keep it `true` even for `WindowsPackageType=None`.
- [winui3-aot-payload-trim.md](winui3-aot-payload-trim.md) — the self-contained Windows App SDK 2.4 payload is 131 MB but a hello-world needs 28 files / 47 MB; what is safe to delete, what is not (`Microsoft.ui.xaml.resources.19h1.dll`, `Microsoft.UI.Xaml.Internal.dll`), and the two hooks used (component packages + `TrimWindowsAppSdkPayload` target).
- [usergpupreferences-holds-non-app-values.md](usergpupreferences-holds-non-app-values.md) — `UserGpuPreferences` also holds `DirectXUserGlobalSettings` and `GraphicsFeaturesNotificationConfig`, so app entries are recognised by `Path.IsPathFullyQualified`; the two mechanisms are keyed differently (full path vs bare exe name), which is why one override can force several rows; flag strings must round-trip unknown flags.
- [winui3-publish-does-not-copy-content-assets.md](winui3-publish-does-not-copy-content-assets.md) — `<Content Include="Assets\...">` reaches the build output but never the publish output, so anything using a file *path* (`AppWindow.SetIcon`) dies only when published, with the same `0xC000027B` as a missing PRI; fix is to read the icon out of the exe. Also: a stale `Assets\` left over in a spike's publish folder will send the diagnosis the wrong way.
- [gameconfigstore-is-the-real-game-list.md](gameconfigstore-is-the-real-game-list.md) — store libraries name the wrong executable (Wuthering Waves, Riftbreaker, Control), so games are discovered from Game Bar's `GameConfigStore` instead; 64 of 108 children are account-synced noise with no `MatchedExeFullPath`, `Flags` is not a usable filter, entries are never pruned, and the D3D ETW channels are all disabled Analytic logs that record nothing.
- [gamebar-matches-games-against-a-microsoft-list.md](gamebar-matches-games-against-a-microsoft-list.md) — Game Bar does not observe games, it matches them against a downloaded Known Game List (`KnownGameList.bin`, `KGLRevision`), so `ExeParentDirectory`/`WorkingDirectory` are match constraints rather than path fragments and `Revision` tells a list match from a manual one; a game moved out of its constraints (Wuthering Waves off Steam) is never recorded, and its stale entry is never corrected — the escape hatches are `RunningGameProbe` and Win+G → "Remember this is a game".
- [aot-link-step-needs-vswhere-on-path.md](aot-link-step-needs-vswhere-on-path.md) — `dotnet publish` dies in the AOT link step with `MSB3073` and a full path to `link.exe`, but the real cause is `vswhere.exe` not being on PATH; also, piping the publish through `tail` reports exit code 0 and hides the failure entirely.
- [winui3-aot-traps-from-meridian.md](winui3-aot-traps-from-meridian.md) — NativeAOT traps already paid for in the Meridian project: `ItemsSource`+`ObservableCollection` crash, `{Binding}` in DataTemplates, `VisualTreeHelper` before layout, `Flyout.ShowAt` XamlRoot, DPI awareness with a custom `Main`.
- [msi-rebuild-needed-when-only-the-version-changes.md](msi-rebuild-needed-when-only-the-version-changes.md) — `-p:ProductVersion=` alone does not make MSBuild rebuild the MSI, so a release can silently ship an installer stamped with the previous version; build with `-t:Rebuild` and verify the version back out of the finished .msi.
- [wix-files-harvesting-fails-ice-in-per-user-msi.md](wix-files-harvesting-fails-ice-in-per-user-msi.md) — `<Files>` harvesting into a per-user install location fails with ICE38/ICE64/ICE91, and FireGiant's documented workaround (`Scope="perUserOrMachine"`) produces the identical failure; the three are suppressed deliberately, with the reasoning per-ICE.
- [per-user-msi-still-registers-arp-under-hklm.md](per-user-msi-still-registers-arp-under-hklm.md) — a `Scope="perUser"` MSI installs with no elevation (log-confirmed) but Windows Installer writes the Uninstall key to HKLM anyway, so winget always reports it as `ARP\Machine`; measured key-by-key, and the reason `Scope` is deliberately absent from the winget manifest.
- [winget-motw-only-bites-untrusted-sources.md](winget-motw-only-bites-untrusted-sources.md) — winget applies a Mark-of-the-Web to every installer it downloads, but only runs the `IAttachmentExecute` scan (antivirus + SmartScreen) when the *source* is untrusted; the community repo is `Trusted`, so a security-check failure under `winget install --manifest` says nothing about the published package. Why unsigned is viable for us.
